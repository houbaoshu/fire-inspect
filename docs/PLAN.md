## 0. 基线摘要（只读本计划所需的上下文）

- **产品**：围绕"一次检查（Inspection）"组织数据。AI 从视频/照片/录音/文字中整理**检查事实 + 证据**，人工确认后查询法规知识、生成三类文书初稿（监督检查记录表 / 照片文书 / 询问笔录），填充进用户上传的 Word 模板导出。全程有右侧全局 AI 助手。
- **部署**：单机构内网、单机 docker compose，**零公网依赖**；所有 AI 能力端点可配置（澄清 §1）。
- **视频规格**：典型 1 分钟 / 60MB / MP4，普通上传 + 短异步任务即可（澄清 §2）。
- **ASR**：DashScope 兼容网关 `qwen3-asr-flash` 已验证通过，**禁止重复付费验证**。无时间戳能力，采用**双跑方案**：整段转写（干净文本→事实提取/笔录）+ 客户端 10s 窗口分段（+1s 重叠，时间锚点→证据回溯）。说话人分离**不要求**（澄清 §6）；"问/答"归属用 LLM 语义方案（已验证，`qwen3.7-flash` 级别模型一次调用出结构化 JSON），用户逐段确认。
- **模板识别**：三份验收模板无任何机器友好机制（无占位符/控件/下划线空白），8 种填充形态、6 类填充操作，**确定性规则引擎即可接近 100% 识别**（TEMPLATE-ANALYSIS §4.3 六条规则）。验收集 = `docs/` 下三份真实模板，目标覆盖率 100%（澄清 §5）。
- **填充样式**：笔录与照片文书填入值带下划线（`w:u val="single"`，标签不动）；记录表检查类型 `□→☑` 打勾；照片文书按关键帧整块纵向重复；笔录问答正文整体生成并带下划线；笔录页脚硬编码"共 4 页"需修正为动态页数。
- **知识库**：预置《消防法》条款级切分（第 X 条）入库并标记"正式法律法规"；其余文档由管理员上传，类型需区分（澄清 §4）。
- **留痕**：事实重要修改与文书确认需**可查看的历史记录**（谁/何时/对象/旧值→新值），文书状态变化也入历史（澄清 §7）。
- **降级**：外部 AI 不可用时，不丢原始数据、不伪造结果、保留人工查看/编辑/整理能力（PRD §14）。

## 1. 技术选型（固化）

选型约束：内网单机部署、零公网依赖、AI 端点全部可配置可替换、分钟级单文件媒体处理、规则引擎覆盖模板识别。

### 1.1 选型对比与决策

每个选型项给出 ≥2 个候选，统一按 5 个维度对比：

1. **零公网依赖** — 内网单机、离线交付与运行的可行性；
2. **工期** — 对 MVP 约 20 人日的影响；
3. **难点适配** — 三大核心难点：Word 无占位符模板填充、ffmpeg 媒体流水线、五组 AI 端点调用；
4. **AI 生成熟练度** — AI 代码生成对该栈的输出质量（本项目主要开发方式）；
5. **内网维护成本** — 组件数、备份升级、无专职运维前提下的可维护性。

跨项背景：ASR 调用与 docx 结构解析两份 spike 均为 Python 脚本且已验证通过，**栈切换 = spike 作废重写**，这构成工期维度上的系统性偏向，下面逐项检验该偏向是否成立。

#### 1.1.1 后端框架 → FastAPI（Python 3.12）（维持）

候选：FastAPI ／ Spring Boot 3（Java 17）／ NestJS（Node 20 + TS）

| 维度 | FastAPI | Spring Boot | NestJS |
|---|---|---|---|
| 零公网依赖 | pip lock 离线安装，镜像内构建 | Maven 离线仓库可行但配置繁琐 | pnpm 离线 store 可行 |
| 工期 | **最省**：两份 spike 可直接搬进生产代码 | 样板代码多，spike 全部作废 | 中等，spike 逻辑需翻译为 TS |
| 难点适配 | python-docx/lxml（见 §1.1.4）；ffmpeg 子进程编排 spike 已调通；httpx 直连五组 OpenAI 兼容端点，与 spike 同形态 | POI 可用（见 §1.1.4）；ffmpeg/HTTP 无差异 | **Word 生态不适配**（见 §1.1.4，一票否决） |
| AI 生成熟练度 | 高；媒体/docx 处理函数与 API 同语言，生成与审查集中 | 高，但 XML 级操作代码冗长，生成错误率上升 | 高 |
| 内网维护成本 | 单 uvicorn 进程 + 内嵌 worker，镜像含 ffmpeg 一体化 | JVM 内存占用高，需调优 | 需另管 Node 生产运行时 |

- **维持理由**：唯一可零翻译复用两份已验证 spike 的选项；最难的"无占位符模板识别填充"其最优库生态在 Python；其余维度无劣势。
- **落选理由**：
  - *Spring Boot*：工程能力无问题，但 Java 样板 + POI 冗长 API 会在 20 人日内挤占难点开发时间；切换后 spike 作废且无对等收益。
  - *NestJS*：Node 的 docx 生态（docxtemplater 等）以占位符模板为前提，直接违反 PRD §8.1"不得要求预先添加占位符"，核心难点不成立，一票否决。

#### 1.1.2 前端框架 → Vue 3 + Vite + TS + Element Plus（维持）

候选：Vue 3 + Element Plus ／ React 18 + Ant Design 5 ／ 服务端渲染（Jinja2 + HTMX）

| 维度 | Vue 3 + Element Plus | React + Ant Design | SSR + HTMX |
|---|---|---|---|
| 零公网依赖 | 构建产物纯静态、内嵌后端伺服；组件库无外链字体（构建时核查无 CDN 引用） | 同左 | 最简 |
| 工期 | 表单/表格/上传组件开箱即用，中文后台语料样板最全 | 组件能力等价，JSX 表单样板略多 | 高交互组件需大量手写 JS，工期不可控 |
| 难点适配 | 前端不碰 Word/ffmpeg；真正难点是交互：视频时间点跳转、关键帧网格多选、逐段问/答标注、助手流式面板与导航动作——需客户端状态管理（Pinia），SPA 必需 | 同左 | **不适配**：上述交互超出 SSR 增强模式合理边界 |
| AI 生成熟练度 | 高；SFC 单文件内聚（模板+逻辑+样式），生成 diff 集中、人工审查快 | 高；diff 分散在 JSX/hooks 中 | 中 |
| 内网维护成本 | 无独立前端服务、无 Node 生产运行时 | 同左 | 最低 |

- **维持理由**：与 AntD 能力等价，胜负手在工期——本项目页面形态是"CRUD + 表单密集工作台"（事实确认、模板映射确认、文书编辑），Element Plus 的 Form/Table/Upload 组合在中文后台场景样板最完整、AI 生成一次通过率高；SFC 结构使生成代码的审查更集中。
- **落选理由**：
  - *React + AntD*：无否决项，属同等能力下的工期偏好；表单密集页样板更多、生成 diff 分散，20 人日约束下略慢。
  - *SSR + HTMX*：视频 seek、帧网格、任务状态轮询、助手流式输出均为富客户端交互，SSR 方案会把工期耗在手写 JS 上，落选。

#### 1.1.3 数据库 → PostgreSQL 16 + pgvector（维持）

候选：PostgreSQL + pgvector ／ SQLite + sqlite-vec ／ PostgreSQL（业务）+ Milvus/Qdrant（向量）

| 维度 | PG + pgvector | SQLite + sqlite-vec | PG + 独立向量库 |
|---|---|---|---|
| 零公网依赖 | 官方镜像 docker save/load 离线交付 | 零组件，最简 | 多一个镜像 |
| 工期 | 一套 Alembic 迁移覆盖业务表 + JSONB + 向量列 | 更轻，但并发与一致性需额外处理 | 两套客户端 + 数据一致性逻辑 |
| 难点适配 | 向量规模 = 法规条款级 chunk（千级），pgvector 远超需求；检索可与文档类型/权限等业务过滤**单条 SQL 联查**；jobs 状态机被 worker 与 API 并发读写，PG 行锁/事务稳定；自带全文检索可做向量召回兜底 | **单写锁**：worker 更新任务状态与 API 写审计并发时是真实风险点 | 千级向量规模下无任何收益 |
| AI 生成熟练度 | SQLAlchemy 2 + PG 为最常见组合 | 高 | 中 |
| 内网维护成本 | 单容器 + pg_dump/卷备份 | 备份拷文件最简单，但并发/一致性弱 | 多一个有状态组件，无专职运维时成本最高 |

- **维持理由**：唯一在"向量检索 + 业务联查 + 并发状态机"三点同时无风险的单库方案。
- **落选理由**：
  - *SQLite + sqlite-vec*：嵌入式对单机在维护上确有优势，但 jobs 表并发状态更新与审计并发写入撞单写锁，且向量检索与业务过滤联查需应用层拼接，落选。
  - *PG + Milvus/Qdrant*：千级向量规模用不上独立向量库，组件数 +1 直接抬高内网维护成本，落选。

#### 1.1.4 Word 处理库 → python-docx + lxml 直写 XML（维持）

候选：python-docx + lxml ／ Apache POI XWPF（Java）／ docxtemplater 等 Node docx 库 ／ LibreOffice headless（UNO/宏）

难点适配是决定性维度。需求清单来自 TEMPLATE-ANALYSIS：run 级字符替换（`□→☑` 精确到目标 run，不能整段重写）、空格段替换为带下划线的值 run、表格空单元格写入（含 vMerge 邻接识别、BR 竖排拼接）、占位段落替换为 inline 图片（media 部件与关系 ID 管理）、锚点后生成全新段落（继承格式）、页脚硬编码页数改 NUMPAGES 域。

| 维度 | python-docx + lxml | POI XWPF | docxtemplater（Node） | LibreOffice headless |
|---|---|---|---|---|
| 零公网依赖 | 纯 Python 依赖，离线安装 | Java 依赖，可行 | npm 依赖，可行 | 镜像体积 +500MB 级 |
| 难点适配 | 高级 API 覆盖段落/表格/run；element 对象即 lxml 节点，6 类填充操作均可落到 XML 级精确控制；**spike 已用 stdlib 验证全部目标结构可达** | 能力完整但 API 冗长，同等 run 级操作代码量数倍 | **以占位符模板为前提，直接违反 PRD §8.1** | UNO/宏做 run 级下划线与字符级替换可控性差 |
| 工期 | spike 结论可直接转化为实现清单 | 绑定 Java 栈，联动 §1.1.1 全套切换 | 不适用 | 崩溃恢复、并发包装需自建 |
| AI 生成熟练度 | 高；底层 XML 形态（`w:u`、`w:r`、`w:sdt`、PAGE/NUMPAGES 域）spike 报告已全部列明，AI 可按清单生成 | 中 | — | 低 |
| 内网维护成本 | 无额外组件 | 随 Java 栈 | — | 最重 |

- **维持理由**：6 类填充操作全部可达、spike 已验证结构假设、与后端同语言。
- **落选理由**：*POI*（栈切换成本 + API 冗长）；*docxtemplater*（占位符前提，一票否决；其余 Node 库面向"生成新文档"而非"识别并原地填充既有模板"）；*LibreOffice headless*（部署重、run 级控制弱，适合格式转换而非精细填充）。

#### 1.1.5 任务调度 → DB 任务表 + 进程内 asyncio worker（维持）

候选：DB 任务表 + asyncio worker ／ Celery + Redis ／ APScheduler

任务特征：分钟级、单文件、短任务（整段转写 1.5–1.7s、分段并行 ~1s、抽帧秒级，见 ASR-VERIFICATION §2/§4）。PRD §4 的核心诉求——逐步骤状态展示、失败原因、重试入口、单步失败不丢已成功结果——本质是**状态机建模**，不是消息队列能力。

| 维度 | DB 表 + asyncio worker | Celery + Redis | APScheduler |
|---|---|---|---|
| 零公网依赖 | 无新增组件 | Redis 镜像 +1 | 无新增组件 |
| 工期 | 状态机/重试/错误原因天然落 jobs 表，UI 直查 | 进度与错误仍需回写 DB 供 UI 查询，等于状态双写 | 不适配 ad-hoc 任务流，需另建状态层 |
| 难点适配 | 媒体流水线各步骤 = jobs 表一行，断点保留（PRD §4）直接成立 | 能力过剩 | **面向 cron 定时调度**，与"上传即触发、按步骤拆子任务"不匹配 |
| AI 生成熟练度 | 高 | 高 | 高 |
| 内网维护成本 | 最低 | broker 为有状态组件，运维 +1 | 低 |

- **维持理由**：在单机分钟级任务规模下，Celery 的分布式能力无使用场景，而状态机需求恰好是 DB 表的天然表达。崩溃恢复对策：启动时将超时"处理中"任务重置为"待处理"；并发用 asyncio 信号量限制，避免打爆 AI 端点与本机 CPU。
- **落选理由**：*Celery + Redis*（组件与状态双写成本，无对等收益）；*APScheduler*（调度模型不匹配）。

#### 1.1.6 部署形态 → docker compose 双服务（维持）

候选：docker compose（app + db） ／ 单容器 all-in-one（supervisord 同管 app + postgres） ／ 裸机安装包（systemd + 本机 Python/ffmpeg/PostgreSQL）

| 维度 | compose 双服务 | all-in-one 单容器 | 裸机安装包 |
|---|---|---|---|
| 零公网依赖 | 两镜像 `docker save` 成 tar，内网 `docker load` + `compose up` | 同左 | **目标机需自装 Python/ffmpeg/PG，内网常无 yum/apt 源，依赖安装即死路** |
| 工期 | Dockerfile 多阶段构建（前端产物内嵌 app 静态目录）一次投入，阶段 7 验收直接复用 | 同左 | 安装脚本需适配各发行版，工期黑洞 |
| 难点适配 | 无差异（ffmpeg 打进 app 镜像） | 同左 | 同左 |
| AI 生成熟练度 | 高 | 高 | 中 |
| 内网维护成本 | 重启策略/日志/卷备份标准化；db 可独立升级备份 | **两进程生命周期耦合**，DB 备份升级别扭 | 环境漂移、多机一致性差 |

- **维持理由**：澄清 §1 明确建议"一体化安装包 / docker compose 单机部署"；compose 在交付、维护、验收（干净机器 `compose up`）三个环节均为标准答案。
- **落选理由**：*all-in-one*（违背容器单一职责，DB 生命周期被绑架）；*裸机安装包*（内网无包源 + 环境漂移）。

#### 1.1.7 决策汇总

六项对比中"AI 生成熟练度"无显著区分度（所列主流栈均为高熟练），选型实际由**工期（spike 复用）**与**难点适配（Word 库生态、任务状态机、向量联查）**决定；六项全部维持原选，均非默认而是对比后的结论。

| 层 | 定型选型 | 决定性理由（详见上文对应小节） |
|---|---|---|
| 后端 | **Python 3.12 + FastAPI** | spike 零翻译复用；Word 生态（§1.1.1） |
| 前端 | **Vue 3 + Vite + TypeScript + Pinia + Vue Router + Element Plus** | 表单密集页工期；SFC 审查集中（§1.1.2） |
| 数据库 | **PostgreSQL 16 + pgvector** | 向量+业务联查+并发状态机单库解决（§1.1.3） |
| ORM/迁移 | SQLAlchemy 2 + Alembic | 随后端栈 |
| 文件存储 | **容器内本地卷**（media/、exports/），DB 存相对路径 | 单次检查材料百 MB 级，单机磁盘足够（澄清 §2） |
| 异步任务 | **DB 任务表 + 进程内 asyncio worker** | 状态机建模而非 broker 能力（§1.1.5） |
| 媒体处理 | **ffmpeg** + Pillow + imagehash | ASR-VERIFICATION 已验证的预处理链路 |
| Word 处理 | **python-docx + lxml 直写 XML** | 6 类填充操作全部可达（§1.1.4） |
| AI 调用 | **httpx 直连 OpenAI 兼容端点**，按能力分五组配置 | 与 spike 同形态，零 SDK 锁定 |
| 认证 | **会话 Cookie（HttpOnly）+ bcrypt** | 单机构内网，无 SSO 要求 |
| 部署 | **docker compose 双服务**：`app`（FastAPI + 内嵌前端静态产物 + ffmpeg）+ `db`（postgres+pgvector） | 澄清 §1 命中；离线 tar 交付（§1.1.6） |
| 包管理 | 后端 pip/uv + lock 文件；前端 pnpm | 构建离线可复现 |

### 1.4 核心数据模型（逻辑视图，建表细节在阶段 0 迁移中定稿）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | username, password_hash, role(inspector/admin) | 角色仅两类（澄清 §1） |
| `inspections` | unit_name, address, inspected_at, 基础信息 JSON, created_by | 一次检查 |
| `materials` | inspection_id, type(video/photo/audio/other), file_path, duration, meta | 原始材料，任何处理失败不得删除 |

| `transcripts` | material_id, kind(full/window), ｜ `transcript_segments`: start_ms, end_ms, text, **speaker（预留扩展位，澄清 §6）**, qa_role(问/答/未标，人工确认) | 双跑产物分开存 |

| `documents` | inspection_id, template_id, doc_type, name(默认=单位+文书类型), status(初稿/已确认), file_path | 三类文书 |

### 1.5 关键机制决策

1. **处理状态机**：`待处理 → 处理中 → 成功 / 失败(可重试)`，UI 逐步骤展示状态、失败原因、重试入口（PRD §4）。
2. **转写双跑**（ASR-VERIFICATION §4）：ffmpeg 抽 16kHz 单声道音频 → 整段一遍 + 10s 窗/1s 重叠分段多遍（可并行）。笔录正文用整段文本，时间锚点用分段文本。
3. **关键帧策略**（澄清 §3）：面向人工选图——均匀+场景变化抽帧 → 模糊/过暗过滤（拉普拉斯方差、亮度阈值）→ phash 相似去重 → VL 生成画面描述候选。数量适中，不做海量抽帧。
4. **问/答归属**：LLM 语义切分轮次 + 预标"问/答"为**候选**，UI 逐段确认/修改；不得猜测身份（PRD §7.3、澄清 §6）。
5. **模板识别**：确定性规则引擎（非 AI），按 TEMPLATE-ANALYSIS §4.3 六条规则优先级实现；规则 1–3 高置信直接采用，4–6 中低置信**展示确认后固化**。未知形态（下划线空白、内容控件）预留规则接口，不纳入本次验收。
6. **模板填充**：实现 6 类操作（空单元格写入 / `□→☑` 字符级精确定位替换 / 标签后追加带下划线 run / 空格段替换为带下划线值 run / 占位段落替换为 inline 图片 / 锚点后生成全新下划线段落）；笔录页脚硬编码总页数修正为 NUMPAGES 域；照片模板 US Letter 纸型保持原样。
7. **文书共享字段**：同一检查的三类文书共享事实、证据、转写、基础字段；共享字段（拍摄地点/摄制人/确认人等）单点维护、改动自动同步（PRD §16）。照片文书"反映内容/说明"逐帧，其余四字段同源只维护一次。
8. **文书状态与重新处理**：模板识别/生成规则升级后已有初稿可重新处理；**已确认文书内容发生变化 → 自动退回初稿**并进历史（PRD §16）。用户改过（origin=user）的字段，AI 重新生成时默认保留并提示。
9. **AI 助手**：右侧面板，后端注入当前上下文（检查/页面/文书/事实/选中的证据），回答仅限当前用户有权限的数据；助手返回**导航动作**（跳视频时间/开照片/开法规原文/定位文书字段），由前端执行，不自主改数据（PRD §13）。
10. **前端路由**：history 模式 + 后端 SPA fallback（未知非 /api 路径返回 index.html），保证刷新/直达不 404（PRD §16）。
11. **初始化/重置**：`seed` 脚本建测试账号（admin / inspector，密码仅用于验收环境）、预置消防法条款级数据、预置三份模板；`reset` 脚本清库+清文件卷后重跑 seed（PRD §16）。

## 2. 分阶段实施

每阶段标注：目标 / 任务 / 覆盖的 PRD §15 P0 条目 / **验收口径**。阶段间有依赖关系，顺序执行；每阶段验收通过后进入下一阶段。

### 阶段 0 — 工程骨架与基础能力（约 2 天）

**目标**：可跑的骨架：compose 起服务、登录、留痕、种子数据、SPA 路由。

**任务**：
- 仓库结构、Dockerfile.app（含 ffmpeg）、docker-compose（app+db/pgvector）；`.env.example` 列出 §1.2 全部变量。
- Alembic 初始迁移（users/inspections/audit_logs 先行，其余表可随阶段增量迁移）。
- 登录/登出、会话鉴权、角色（inspector/admin）中间件、AI 助手与 API 统一鉴权。
- audit_logs 写入与通用查询接口。
- 前端骨架：登录页、主布局（含右侧助手面板占位）、路由 fallback。
- seed/reset 脚本；消防法 PDF（`testdata/knowledge/`）条款级切分入库（第 X 条 chunk，标记"正式法律法规"）。

**P0 覆盖**：基础身份、权限和操作留痕（部分：留痕查看 UI 在阶段 2/5 随业务页面落地）。

**验收口径**：
- `docker compose up` 后注册路由可访问；刷新/直达任意业务路由不 404。
- admin/inspector 测试账号可登录；无会话访问 API 返回 401。
- 一条手工触发的审计记录可在接口中查到（谁/何时/对象/旧值→新值）。
- 消防法条款可通过 SQL 查到，每 chunk 带"第 X 条"标签。
- 全链路无任何公网请求（前端无 CDN 字体/脚本，断外网可运行）。

### 阶段 1 — 检查管理与媒体处理流水线（约 4 天）

**目标**：创建检查 → 上传材料 → 转写双跑 + 关键帧提取，状态机完整。

**任务**：
- 检查 CRUD、材料上传（视频/照片/录音/其他）、材料列表与预览。
- jobs 任务表 + 进程内 worker；逐步任务：抽音频 → 整段转写 → 窗口分段转写 → 关键帧提取（过滤/去重/VL 描述）。
- ASR 客户端按 ASR-VERIFICATION §1 调用形态实现（OpenAI 兼容、`input_audio` base64、`asr_options{language:zh, enable_itn:true}`）；错误解析含"400 空错误体"形态，失败原因入库展示。
- 转写结果页：整段文本 + 分段（时间范围）视图；点击分段可定位。
- 关键帧网格页：候选帧预览、删除错误候选、补充上传照片（作为无时间戳关键帧）。
- AI 不可用降级：任务失败可重试，原始材料与已成功步骤结果完好，材料可人工查看。

**P0 覆盖**：一次检查的创建和管理；视频/图片/录音等材料上传；视频转写和关键画面提取。

**验收口径**：
- 用 `testdata/videos/1.mp4`、`4.mp4`（约 48s）走通：上传 → 双跑转写成功 → 分段带时间范围且与 ASR-VERIFICATION §4 结果一致量级（5 段上下，窗长/重叠可调）。
- 关键帧：覆盖全程关键时刻、模糊/过暗帧已剔除、无肉眼重复帧；数量适中（分钟级视频 ≲ 30 帧候选，可调）。
- 停掉 AI 端点重跑：任务进入"失败(可重试)"并显示原因，材料与已成功步骤不丢；恢复后端点重试成功。
- 单步失败（如 VL 描述失败）不影响转写与抽帧结果展示。

### 阶段 2 — 检查事实与证据回溯（约 3 天）

**目标**：从转写/关键帧/用户补充中提取候选事实，人工确认，事实↔证据关联并可回溯。

**任务**：
- LLM 事实提取（整段转写 + VL 帧描述 + 基础信息 → 候选事实 JSON），状态"候选"。
- 事实工作台：确认/修改/删除/补充事实；共享事实池供后续文书复用。
- fact_evidences 关联 UI：事实挂视频时间段、关键帧、转写分段；支持多文件，证据记录 material_id。
- 证据回溯：事实详情点击证据 → 视频跳到对应时间（正确文件）、预览图片、查看转写段。
- 事实修改历史页（澄清 §7）：事实详情可查旧值→新值。

**P0 覆盖**：候选检查事实生成和人工确认；共享检查事实；事实与证据关联；视频、照片证据回溯（法规回溯在阶段 3）。

**验收口径**：
- 样本 1（控制室无人值班场景）：AI 候选事实中包含"无人值班/持证"相关事实；样本 2（大厅堆物）类似。
- 事实确认后修改留痕可查。
- 每条已确认事实至少可挂 1 条证据；点击视频证据跳转到**正确文件的正确时间**（存在多个视频时不串）。
- 无法可靠识别的信息不被臆造：提取 prompt 要求"不确定则标待确认"，验收时抽查无不实生成。

### 阶段 3 — 法规知识库与检索（约 3 天）

**目标**：知识文档管理 + 条款级检索问答 + 来源可追溯。

**任务**：
- 知识文档上传/删除（admin），解析管线：docx/pdf 文本抽取（pdf 用 pdfminer/pymupdf），扫描件走 OCR 兜底（可配）；切分入库 + embedding。
- 文档类型标记（正式法律法规/内部制度/标准规范/其他），UI 展示类型，不得把内部制度标为法规。
- 检索问答接口：文字查询 → 向量召回 → LLM 组织答案，返回：可能涉及的问题、相关条款、原文、适用理由、来源（文档+条款标签），可打开原文核对。
- 结合当前检查事实的查询入口（选事实查法规）。
- 防伪造：回答必须引用检索到的 chunk；无召回时明确告知"知识库中未找到"，不得编造条款。

**P0 覆盖**：知识文档上传；法规/知识查询及来源回溯（文字查询；语音查询为 P1  backlog）。

**验收口径**：
- 用样本事实"消防控制室无人值班"查询：召回消防法相关条款，答案含原文+条款标签+来源，点击可打开原文定位。
- 上传一份内部制度测试文档：类型标记正确，检索可命中且来源标注为该内部制度。
- 查询知识库不存在的内容：系统明确回答未找到，无伪造条款。
- 法规证据可挂到 fact_evidences（类型=knowledge_chunk），事实页可回溯打开。

### 阶段 4 — 模板上传与自动识别（约 4 天）

**目标**：普通无占位符 Word 模板上传 → 规则引擎识别 → 字段映射人工确认 → 固化复用。

**任务**：
- docx 解析层：段落/表格/run/单元格邻接/vMerge/BR 拼接/页眉页脚 的统一抽象（TEMPLATE-ANALYSIS §4.2 难点逐条对应）。
- 规则引擎实现 §4.3 六条规则 + 置信度分级；输出字段清单：稳定中文业务名、定位 anchor、填充操作类型、置信度。
- 识别结果确认 UI：字段列表展示，中低置信字段高亮，允许改名/改类型/删除/补充；确认后存 template_mappings；同模板再次使用直接复用映射。
- 支持显式占位符模板（`{{field}}` 直接识别为高置信）。
- 三份验收模板预置进 seed。

**P0 覆盖**：普通 Word 模板上传；无占位符模板自动识别和字段映射；模板映射人工确认。

**验收口径**（基线 = TEMPLATE-ANALYSIS §3 字段清单，目标 100%）：
- 照片.docx：识别 7 项（照片占位 F + 6 个冒号追加字段），标注同源/逐帧字段。
- 询问笔录.docx：识别 11 项表头字段（含 `第␣次`、起止时间、一行多字段切分——必须靠标签词典而非空格阈值）+ 问答正文生成锚点（形态 G）+ 页脚硬编码页数警告。
- 监督检查记录表.docx：识别 11 项（含 `□` 复选框组、空单元格对、半角冒号编号/日期骨架、竖排 BR 标签拼接、标签后零空白签名行）。
- 不向用户显示任何内部字段键/哈希。
- 修改字段名并确认后，映射入库；重新打开该模板映射直接复用，无需重新识别。

### 阶段 5 — 三类文书生成、填充与导出（约 5 天）

**目标**：基于已确认事实生成三类文书初稿 → 填模板 → 人工编辑 → 导出正式 Word。

**任务**：
- 文书创建：默认名 = 被检查单位 + 文书类型；共享字段从检查/事实单点获取，修改自动同步到各文书。
- 三类生成器：
  - **监督检查记录表**：检查类型映射打勾（`□→☑` 精确定位 run）、空单元格写入、检查内容和情况长文本生成。
  - **照片文书**：关键帧选图（预览/多选/删候选/上传补充）→ 每帧独立证据区块整块纵向重复；反映内容/说明逐帧（VL+事实生成候选，一句话客观描述、限长），拍摄地点/摄制人/拍摄时间/确认人同源只填一次。
  - **询问笔录**：整段转写 → LLM 问答归属候选 → 用户逐段确认/改角色/改文 → 正文"问：/答："格式整体生成（带下划线）；表头字段带下划线填充；页脚总页数修正。
- 填充引擎：6 类操作（§1.5-6），下划线规则按模板类型执行，值 run 继承段落字体字号。
- 文书编辑页：字段级编辑、局部重新生成（origin=user 字段不无提示覆盖）、证据侧栏核对。
- 文书状态机：初稿 → 已确认；已确认文书对应内容变化 → 退回初稿并留痕；确认/回退入历史可查。
- 导出：保持原模板格式的 .docx 下载。

**P0 覆盖**：三类文书生成；Word 模板填充和导出；文书人工编辑。

**验收口径**：
- 三份预置模板各生成并导出一份文书：用 Word/WPS 打开，格式（字体/表格/页边距/纸型）与原模板一致；笔录与照片文书填入值带下划线、标签无下划线；记录表选中项 ☑ 未选项 □。
- 照片文书：2+ 帧区块纵向排列，同源四字段只维护一次且同步，说明≤一句话。
- 询问笔录：正文统一"问：/ 答："；归属候选经人工改后导出一致；超 4 页时页脚总页数正确。
- 人工改某字段 → 触发局部重新生成 → 该字段不被覆盖且有提示。
- 已确认文书的事实/共享字段变化后：文书自动退回初稿，历史记录可查。
- 模板映射/生成规则升级后，已有初稿可一键重新处理。

### 阶段 6 — 全局右侧 AI 助手（约 3 天）

**目标**：上下文感知的统一 AI 入口，可问答、可查法规、可跳转定位。

**任务**：
- 右侧悬浮面板：展开/收起，全业务页面可用。
- 上下文注入：当前检查、页面类型、当前文书/字段、选中事实/证据；后端组装 system 上下文，数据范围按当前用户权限过滤。
- 能力：基于事实/证据/转写/知识库的回答（复用阶段 3 检索）；回答中引用证据。
- 页面联动：助手响应可携带导航动作（跳视频时间、开照片、开法规原文、定位事实、打开文书字段），前端执行跳转；不自主执行修改类操作。
- 简单建议（P1 范围内可裁剪）：如"该事实未关联证据"提示——按进度取舍，不阻塞 P0 验收。

**P0 覆盖**：全局右侧 AI 助手；AI 助手理解当前检查和页面上下文；AI 助手查询、定位并跳转相关内容。

**验收口径**：
- 在事实详情页问"这条内容依据是什么？"→ 回答引用已挂证据并给出跳转；点击后跳到正确视频时间/图片/转写/法规原文。
- 问"这次检查里有没有提到值班人员？"→ 基于本次检查转写回答并定位分段。
- 问法规问题 → 走知识库检索，答案带来源；助手返回的数据不超当前用户权限（用无权限检查验证不出现）。
- 助手不执行任何未经用户确认的写操作。

- 一台干净机器 `docker compose up` + seed 即可验收。
